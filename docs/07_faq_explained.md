# 07 常见问题与通俗解释（FAQ）

> 2026-09-20。面向读者的三问三答：实验纪律、扩展方向、核心实现的大白话解释。

## Q1：基线显示 CPU 空闲，为什么正式实验还要 taskset 固核和标注背景？

**基线空闲 ≠ 永远空闲。** E0 那 60 个样本只是某 2 分钟窗口的快照，它证明"我们采数据时机器没被邻居吵到"——它是**事后检察官，不是事前保险**。

目标节点是**共享机**（705G 内存已被其他租户用了 276G，load 长期在 2-3 波动）。风险在于：

- **不测基线**：如果实验跑出来的"队列等待 p99=1.8s"其实是隔壁在编译内核造成的，我们永远不知道，结论就是废的。有了基线，才能声明"采集窗口内背景负载 0.5%，测量可信"。
- **不固核（taskset）**：Linux 调度器会把 sandbox 进程随意扔到任意核上，可能和邻居进程挤同一组核。这次跑用到空闲核、下次被挤到忙核，**两次实验数据不可比**——扫参实验（4/32/128 workers 对比）最忌讳这个：你分不清差异来自参数还是邻居。
- **固核**：把所有实验进程钉死在 0-63 这 64 个核上，邻居用别的核，我们的数据可复现、可对比。

一句话：**基线是"取证"（证明数据干净），固核是"隔离"（让数据可复现）**。这是共享机器上做性能实验的标准纪律，工业界给 RL 系统做 benchmark 同样这么做。

## Q2：四个扩展方向的详细说明

### E3/E6 引擎画像扫描（节点实验，工作量小）

- **E6**：扫描 llama-server 实例数 × 每实例 slots（1×4 / 2×8 / 4×16 …），测聚合吞吐 tok/s、prefix cache 命中率、以及**推理与 sandbox/driver 抢核**的关系——真实 colocate 部署的核心矛盾。
- **E3**：逐渐加大推理并发，测 driver 进程 CPU 占用，找到 Python driver 的饱和点——直接验证"为什么 DeepSeek 要用 Rust 重写 DSec 网关"这个工程决策。
- 产出：两条曲线 + 一个饱和点数字，回答"rollout 侧 CPU 怎么花掉的"。

### L1/L2 多轮 agentic 闭环（最贴 GLM-5.2 场景）

- 现状是单轮：模型出一次答案 → 判分。L1 是多轮：模型读仓库 → 改代码 → 跑 pytest → 看报错 → 再改……最多 8 轮，**每轮都进一次 sandbox**。
- 要做：rollout_manager 加 agent loop（engine 多轮对话 + 每轮解析 tool call + sandbox 执行 + 结果拼回上下文）。
- 价值：sandbox 到达率被轮次放大 5-10 倍，"长尾轨迹拖住整组"会非常显著——这正是 GLM 做异步流水线（SAO）要解决的真问题，可以亲眼看到。

### SAO 模拟（GLM-5.2 生产的异步范式）

三个机制都能加到现有骨架上：

1. **group size = 1**：去掉组屏障，单条轨迹完成即训；
2. **DIS**：直接用 rollout logprob 当 behavior policy，信任域外 mask——我们已有真实 logprob，改动小；
3. **mock critic**：value baseline 代替组均值。

价值：对比 sync GRPO vs async SAO 的 sandbox 利用率和吞吐，复现"组屏障空转 vs 单条即训"的论文结论。

### OPD 蒸馏模拟（DeepSeek V4 阶段二）

- 钩子已留好：Q8 引擎当"教师"。机制：student 生成轨迹 → 教师对同样本再 forward 一遍拿 logprob → `advantage -= 系数 × (student_logp − teacher_logp)`。
- 双精度配置（Q4 学生 / Q8 教师）天然演示训推不一致 + 蒸馏信号，llama.cpp 即可跑。

## Q3：现在的核心实现是什么？（大白话）

想象一个"AI 集训营"模拟器：

- **题库**（data_source）：一叠练习题卡，每次抽几道，每题复印 8 份（GRPO 的"组采样"）。
- **考生**（engine）：跑在 CPU 上的小模型（llama.cpp + Qwen3-4B），答题时还**如实报告自己每个字的把握**（per-token logprob，真家伙）。
- **考场**（sandbox）：答卷里的代码被扔进**带锁的小黑屋**真实执行——限 CPU（5 秒）、限内存（512MB）、断网（unshare）、以最低权限用户（nobody）运行。死循环被掐表枪毙，爆内存被撑死，全程记录耗时/内存/IO。
- **阅卷**（reward）：对答案给分，全对 1 分、全错 0 分、部分对给比例分。
- **教练组**（rollout_manager）：同一题 8 份答卷拉平比较——"比组内平均分高就是好答卷"（GRPO advantage）。全组同分（全会或全不会）的题直接扔掉不练（DAPO 零方差过滤）。
- **训练房**（trainer）：**唯一演的地方**——不真改权重（没 GPU），但真实计算损失值、clip/TIS 屏蔽比例等标量，然后按 token 数睡一觉（模拟 GPU 耗时），权重版本号 +1。
- **广播**（weight_sync）：训练完"暂停考试 → 通知考生换新脑子 → 恢复考试"，时序全真、传输是假的。
- **摄像头**（monitor）：每个环节掐两块表——墙上钟（wall）和 CPU 工时（cpu），队列深度、启动开销全记录。

**一句话总结**：除了"训练房里真改权重"是装的，整条流水线——出题、答题、进小黑屋执行、判分、算优势、广播新版本——**全是真的在跑**。所以它能量出：RL 后训练里 CPU 到底在忙什么、sandbox 什么时候堵、队伍什么时候排起来。
